## 22:05 干掉 BullMQ：异步消息改用 Kafka

- 背景：用户判定 BullMQ 是垃圾，要求移除并用 Kafka 代替。
- **调查结论（决定了改动性质）**：`QueueManager` / `QueueModule` 在 `apps/server` **零使用**
  （全仓唯一命中是它自己的定义与 `root.module.ts` 的装配），也没有任何单测 ——
  所以这不是「迁移」而是「删除 + 把 Kafka 扶正」。
- 做了：① 删 `packages/kits/src/queue/`（QueueManager / QueueModule / index）、
  `kits/src/index.ts` 的导出、`root.module.ts` 的装配；② kits 依赖去掉 `bullmq`，
  `pnpm-workspace.yaml` 的 BullMQ 相关条目随之清理（lock 已清干净）；
  ③ **退役 `queue` skill**（manage-skills §5）并新建 `kafka` skill（SKILL.md + kafka-guide.md），
  因为此前**没有任何 skill 覆盖 Kafka**——只删不建等于把异步能力变成没人会用的死代码；
  ④ 更新 11 处指向 `queue` skill 的跨引用（develop-backend-api ×5、database ×2、scheduler ×2 等）
  与两处索引（`.agents/skills/README.md`、`billy-dev-foundation/references/catalog.md`）、
  `placement.md` 的归位表（BullMQ → Kafka 门面 +「延迟任务交 scheduler」）；
  ⑤ README（技术表新增 Kafka 行、tree、kits 说明、模块清单、7 处正文）、`docs/queue.md`
  标为已废弃存档、`docs/billy-pitch.md` 与 `docs/design/scheduler.md` 纠偏。
- 关键取舍（写进 kafka skill）：**Kafka 不能 1:1 顶替 BullMQ** —— 它没有 per-message 延迟投递 /
  优先级 / 单条重投，且消费异常只记日志不自动重投。故明确分工：消息 → Kafka；
  延迟 / 周期 → `scheduler`（croner）或 `time-wheel`；失败补偿 → 消费端幂等 + 重试 topic /
  落表补偿。**at-least-once 要求处理器必须幂等**，这条被写进 skill 的检查清单。
- 坑点：① 我第一轮用 perl 批量换 `` `queue` `` 时只覆盖了「queue 在前」的形式，
  剩余 6 处漏改，靠二次 grep 才发现；② 中间一次 grep 模式里用了双引号包反引号，
  bash 把 `` `queue` `` 当命令替换执行（`bash: queue: command not found`），
  **校验结果因此不可信**，改用单引号重跑才确认干净；③ 机械替换把 scheduler.md 的一句改成
  自相矛盾（「定时走本方案的 Scheduler，但不提供进程内定时器/Cron 调度」），逐行读回后修正。
- 验证：源码 + 依赖 + 锁文件 + 文档 + skill 零 `bullmq` / `QueueManager` / `QueueModule` 残留
  （仅 `docs/queue.md` 存档与 kafka skill 的迁移对照表保留说明）；
  `pnpm build:pkgs` 4/4；kits 121 / http-client 95 / server 33 单测全绿；`check:inject` 绿灯；
  `tsc --noEmit` 零错误；**实测启动**：模块列表里不再有 `QueueModule`、健康检查 200、
  请求日志正常。

## 22:25 补齐脚手架的生产级默认：长连接超时 + 三件请求中间件

- 背景：上一轮修好了脚手架的「编译不过」，但它仍是精简骨架 —— 缺 `apps/server` 已有的
  生产级默认。目标：让 `pnpm cli -t service` 生成的骨架与 `apps/server` 对齐。
- 补齐内容（新增 8 个模板文件，`templates/service.ts` 登记）：
  ① `app-config.eta` 的 `server` 分片加 `keepAliveTimeoutMs`（75s）/ `headersTimeoutMs`（80s）
  与 `superRefine`（反序直接启动失败），`mapEnv` 映射 `KEEP_ALIVE_TIMEOUT_MS` /
  `HEADERS_TIMEOUT_MS`；`main.eta` 在 listen 前赋给 `httpServer`；
  ② 三件自注册中间件（按 `apps/server` 的 folder-per-concern 结构原样生成）：
  `common/request-context/`（ALS + 中间件 + 模块）、`common/request-logger/`、
  `common/request-metrics/`，外加 `common/index.ts` 汇总；`root.module.eta` 按
  RequestContext → RequestLogger → RequestMetrics 的顺序装配（顺序铁律写进生成物注释）；
  ③ `RateLimitModule`（无自有配置，排在 RedisModule 之后）。
- 守卫升级：`check:scaffold` 不再手写文件清单，改为直接消费 `createServiceTemplate` 的真实映射
  （只落 `.ts`），**以后新增模板自动纳入检查**；模板数 6 → 14。
- **端到端实测**（不只靠类型检查）：`pnpm cli -t service -n scaffold-probe --no-install` 生成 →
  `pnpm install` → 启动（临时端口 9997）：
  · 启动日志里 RequestContextModule / RequestLoggerModule / RequestMetricsModule /
    RateLimitModule 全部 `dependencies initialized`（DI 与中间件装配都成立）；
  · 响应头 `X-Request-Id: <16 位>` 与 `Keep-Alive: timeout=75`（证明超时默认值真的落到 socket）；
  · 请求日志为单行 `[HTTP] GET / 404 6ms` + 结构化字段，且 `requestId` 与响应头**同值**
    （证明 ALS → 日志这条链路在生成物里是通的）；
  · 负例：`HEADERS_TIMEOUT_MS=70000` 启动即失败、退出码 1，报
    「headersTimeoutMs(70000) 必须大于 keepAliveTimeoutMs(75000)」。
  验证后删除探针应用、`git checkout pnpm-lock.yaml` 并重跑 install，工作区只留模板改动。
- 坑：探针脚本原来只 `mkdirSync(src/lib)`，新增的 `src/common/<子目录>/` 写入报 ENOENT ——
  改为按每个文件的 `dirname` 建目录（与生成器的写法一致）。
