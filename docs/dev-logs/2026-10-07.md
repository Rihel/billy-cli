② `withUserContent` 在末条不是 user 消息时**静默丢附件** → 改为抛错。

**第三轮（用户纠正 + 业界调研）：多模态能力改成模型实体的独立字段**。用户指出"不是有模型配置页面吗？
给模型实体加多个字段"，先做调研再动手：

| | OpenRouter（Models API 标准） | LiteLLM（model_prices_and_context_window.json） |
| --- | --- | --- |
| 形态 | `architecture.input_modalities: ["text","image","file"]` + `output_modalities`（实测 465 个模型，取值 text/image/file/audio/video） | 扁平布尔 `supports_vision`（2234/4485）、`supports_pdf_input`（1015）、`supports_audio_input`（746）、`supports_video_input`（126） |
| 类型 | `architecture.modality` 串 | `mode`（chat/embedding/…，4476/4485 都有） |

结论：**模态是模型的一等属性**。取 OpenRouter 的数组形态（加模态不改表）+ LiteLLM 的 `mode`
（解决"选模型下拉里混进 embedding"，选中了必然报错）。落地：`ai_models` 新增
`mode` / `input_modalities` / `output_modalities`（迁移 `1791345374191`），`capabilities` 语义收窄为
"供应商原始标记留存"，判能力一律看模态。**三态**：`null` = 未声明（**不拦**，只提醒 ——
国内厂商普遍不给模态，硬拦会误伤真正的视觉模型）/ `[]` = 明确什么都不支持 / `["text"]` = 只收文本。
适配器认 OpenRouter 的 `architecture.*`、LiteLLM 的布尔位、顶层 `input_modalities` 与
`capabilities` 里的词（`vision`→`image`、`pdf`→`file` 同义词）；**认不出落 null，绝不编造**
（包括不把输出默认成 `["text"]`：清单里混着 embedding / 图像生成）。同步时
`input.inputModalities ?? existing.inputModalities` —— 供应商没给就保留人工填的。后台模型页加
「类型」下拉与「输入/输出模态」多选，列表加类型与输入模态列；标签词已存库。

**第五轮（用户报"发图但模型说没收到"，实为真 bug 且极难定位）**：症状像"模型不支持读图"，
实际与模型能力无关。排查路径（每个环节单独测都是对的）：时间线 payload 有附件 ✅ → MinIO 能读 ✅ →
服务端诊断日志显示 `kind:"image"`、注入后末条 content 为 `["text","image"]` ✅ → 抓 fetch 发现 Mastra
在 `generate`/`stream` 两条路径下都能发出图 ✅ → `durable` 开关无影响 ✅ → 同 key 同模型直发上游
（1.86MB data URL）200 且读出了图 ✅。**最后靠出站抓包抓到真实请求**：`requestBytes: 27318,
hasImageUrl: false` —— 图根本没发出去。

根因：Mastra 的 `Agent` 允许把 `model` 写成**函数**（动态参数，我们最初就用它做"每轮可选模型"），
但那条路径会把多模态 `content` 数组**压平成纯字符串**。A/B 实测（同图同适配器）：
Agent 挂动态 model + 调用时不传 model → **156 字节**、`content: "看图"`；调用时显式传模型实例 →
**289KB**、含 `image_url`。修法：`toMastraModelInstance` + 每轮显式 `agent.stream(..., { model })`，
非流式 / 流式 / 子 agent 三处都传。

**为什么原测试没拦住**（教训）：那条"带附件"的 e2e 只走**非流式**（用户走流式），且用 mock 走
**通用兼容**路径、不经过官方适配器 —— 而压平只在官方适配器那条路现形。补的防线是契约测试：
断言 `toMastraModelInstance` 返回**带 `doStream`/`doGenerate` 的真实例**而非配置对象。

**第五轮定论（更正上一轮的错误结论）**：上一轮我把根因写成"Mastra 的动态 model 参数压平多模态"——
**那是错的**。真实根因是 **`durable: true`（崩溃恢复，线上默认开）**：`@mastra/core@1.69.0` 在
durable 下把 `content` 数组压平成纯字符串，出站请求只有 **156 字节**、`content: "看图"`；
`durable: false` 正常；**升到 `1.75.0` 后 durable 下也正常**（上游已修）。我们的代码从头到尾是对的。

定位方法（这轮才走对）：**不再逐环节证明"某环节没问题"，而是自己端到端跑真实链路 + 抓出站请求**。
为此临时把服务端跑起来（`AUTH_ENABLED` 临时关掉试过、最后改成给自己签发 token），
再用一张**自己构造的"左半红右半蓝"小图**（1102 字节）发问："左右半边分别是什么颜色"——
修复前出站请求无 `image_url`，修复后能，且模型答"左半边红色，右半边蓝色"。

**为什么藏了这么久**（三条教训）：① 逐环节证明"每个环节都正常"不等于定位了问题；
② 我的实验一律用 `new Agent()`（默认非 durable），而生产是 `createMastraAgent({ durable: true })` ——
实验环境与生产不一致是最贵的坑；③ 早期 A/B 没控制 durable 变量，得出并写进了错误结论，
**A/B 必须只改一个变量**。这三条已写进设计文档 §3.16.2.1。

回归防线：`ai-mastra-contract.test.ts` 新增"durable 下的多模态"——断言 durable agent 出站请求的
`user.content` 是 part 数组且含 `image_url`（压平时是纯字符串），**必须走 durable 才有效**。

**第六轮（用户问"durable 是什么、我们有用吗"，顺手挖出第二个洞）**：先说清 durable 是什么
（已补进设计文档 §3.0.0：一句话定义 + 没有它会怎样 + 它怎么做到 + 代价 + 开关 + 两次踩坑），
然后核实"我们真的在用吗"——**在用，且默认开**（`durableEnabled` 默认 true、已传进 createMastra、
启动恢复每次都在跑）。但核实过程中发现：

**`runs.engine_run_id` 一直是空的，"崩溃后能续跑"从未真正生效**。快照落库是
`UPDATE runs SET snapshot ... WHERE engine_run_id = :runId`，id 对不上就丢快照
（`ai.storage.snapshot_orphan_skipped`）。而 `engine_run_id` 没人写：`markRunning(run.id)` 没传第二个
参数，唯一能补的 `attachEngineRun` **在源码里零调用**（注释却写着"已在 chat.service 修"，
实现与文档脱节；查 git 全历史也从未调用过，库里 60 条运行只有 13 条早期手工造的带快照）。

修法：**引擎 runId 由我们定**（`eng_<我们的 runId>`），起跑时回写进 `runs.engine_run_id`，
并同时交给 Mastra（`agent.stream(..., { runId })`），两边用同一个 id。
实测验证：修复后那一轮 `engine_run_id = eng_<runId>`、`snapshot` 23.7KB 真的落库、
`snapshot_orphan_skipped` 归零。回归防线：流式 e2e 断言引擎 id 回写
（`ai-storage-recovery.test.ts` 已覆盖快照落库机制本身）。
