## 00:40 修复：web 首页登录后仍显示登录按钮

- 反馈：「web 的首页，在登录后还是会显示登录按钮」。
- **先复现（关键）**：用 headless Chrome + CDP 跑真实登录流程实测 —— 顶部导航是「活」的
  （登录后正确切成头像 + 用户名 + 退出），真正的锅是**三处写死的静态账号入口**：
  Hero 主视觉的「登录 / 开始使用」、底部 CTA 区的「创建账号 / 登录」、页脚「账号」分组
  （登录 / 注册 / 忘记密码 / 重置密码）。它们都是静态 Server Component，拿不到登录态，
  只有 Header 自己在客户端读 localStorage + `getMe()` 探测（还带来首屏先闪「登录/注册」的抖动）。
- 做了：web 根 layout 本就是 `force-dynamic`（每次请求 SSR），故**对齐 admin 的既有模式**，
  改为服务端 cookie 会话探测：
  ① 新增 `apps/web/src/lib/auth-session.ts`：`getAuthEnabled()` / `getAuthUser()` /
  `getWebAuthState()`（React `cache()` 包裹，同请求只请求后端一次）——读 httpOnly cookie →
  `auth.getMe()`，会话失效或无 cookie 返回 `null`（前台不强制登录，不跳转）；
  config 获取失败保守按「开启」处理（与 admin layout / proxy 同策略）；
  ② `app/page.tsx` 取一次状态，把 `user` / `authEnabled` 下传；
  ③ Header 去掉两个客户端 useEffect（config + localStorage getMe），改受控 props，
  登出后 `router.refresh()` 让 RSC 用新 cookie 重渲染；
  ④ Hero / CtaSection / Footer 已登录时不渲染账号入口，页脚「账号」分组整组隐藏且
  网格列数自适应（3 列 → 2 列）。
- 验证：web `tsc --noEmit` 0 错误；CDP 四步回归全绿 —— 未登录 5 个登录链接 → 登录后 **0 个**、
  页脚分组变「产品 / 服务」→ 硬刷新仍为登录态（SSR 生效，无闪烁）→ 点退出恢复未登录。
- 文档/skill：implement-auth 的 auth-guide §5 补「SSR 会话探测（web 前台页）」条目。

## 22:35 新增运维探针接口（根路径 GET /healthz、/readyz、/info）

- 背景：k8s `httpGet` 探针**只会发 GET**，而全仓业务路由统一 POST、`POST /monitor/health`
  还「依赖失败也返 200 + degraded」—— 探针会 404 / 永远就绪，滚动更新时新 pod 未就绪就接流量。
- 做了：① 新增 `modules/ops`（`OpsController` + `OpsModule`，组合根注册）：`GET /healthz`
  **刻意不探外部依赖**（liveness 探依赖会让依赖抖动触发全量重启雪崩）、`GET /readyz` 探 DB / Redis
  且失败返 **HTTP 503 + code 5002** 主动摘流（用 `BoundaryError` 而非 `AppError`：边界错误不打错误日志、
  不触发告警，否则每 3s 一次变告警风暴）、`GET /info` 暴露版本 + 运行时 + **已生效的长连接超时**
  （排查 502 竞态时可直接看实际值）；② 探活加 2s 超时（依赖假死不能挂住探针）；③ `ErrorHttpStatus`
  放行 503 + 新增 `NotReady`(5002/503)；④ `server` 配置加 `appVersion`（env `APP_VERSION`，默认 `dev`）；
  ⑤ 新增 `common/http/ops-probe.ts`，请求日志与请求指标**跳过** `/healthz`、`/readyz`（`/info` 照常记）。
- 验证：tsc 0 错误；server 单测 46（新增 13）；`check:inject` 通过；另用**临时脚本起真实 HTTP**
  实测 6 条（healthz 在 DB/Redis 全挂时仍 200、readyz 正常 200、DB 挂 / Redis 挂各自 503 + code 5002 +
  中文指明依赖、info 返 version 与 75000、POST /healthz 为 404），验完即删。
- 坑点：① `ErrorHttpStatus` 原本没有 503，`ServiceUnavailableException` 会被 `mapError` **收敛成 500**，
  故必须显式放行 503；② 探针若不排除出指标，`request.error` 会被探针自身的 503 抬高 → 错误率告警失真。

## 23:14 修复优雅关闭被 SSE 长连接挂死（滚动更新 502 的另一半根因）

- 问题：`main.ts` 的 `app.close()` 会被 SSE 长连接**永久挂起** —— SSE 路由 `await connection.closed`
  挂起长连接，`server.close()` 回调就永不触发；进程只能等 `terminationGracePeriodSeconds` 到点被
  SIGKILL，在途的普通请求跟着一起死（502）。原先 `StreamHub.onApplicationShutdown()` 只 quit 了
  pub/sub，没有关闭任何连接，且它在 `httpServer.close()` **之后**才执行（顺序上就晚了）。
- 做了：① `StreamHub` 改为实现 `BeforeApplicationShutdown`，在 `beforeApplicationShutdown()`
  里给每条连接推 `stream.shutdown`（新增 `@repo/shared` 常量）再关闭，并把排空中到达的新连接立即关闭
  （否则它会重新挂住关闭流程）；② 客户端 `HttpStreamClient` 收到 `stream.shutdown` 标记
  `serverShutdown`，流结束后**立即重连**而不是进入 `closed` 终态（必须先于「正常结束」判断），
  且该判断独立于业务监听器；③ `main.ts` 关闭流程加 `SHUTDOWN_TIMEOUT_MS`（默认 25s）兜底，
  超时记 error 后强制退出，并在日志里打出关闭耗时。
- 关键取舍：客户端原来把「服务端正常 end()」当终态（不重连）。若只做服务端排空而不加 shutdown 事件，
  滚动更新会让长连接**静默失效**——比 SIGKILL 更糟（SIGKILL 属异常断开，反而会触发重连）。
- 验证：**对照实验**（真实 HTTP 长连接 + 临时脚本，验完即删）—— 对照组（无排空）
  `app.close()` 1502ms 超时未关闭（复现挂死）；实验组（先排空）**2ms 正常关闭**。
  单测：kits 129（+3 排空用例）、http-client 96（+1 重连用例）、server 48（+2 关闭配置用例）；
  `tsc` 0 错误、`check:inject` 通过。
- 文档/skill：README「前置反向代理」新增第 4 条（优雅关闭 + k8s 配套）、`.env.example` 补两个变量；
  stream skill 补排空协议与客户端重连；foundation / develop-business-module 补「业务路由全 POST 的
  唯一例外是 ops 探针 GET」。

## 23:35 落地 k8s/server 部署清单（滚动更新不 502 的集群侧那一半）

- 背景：应用侧两个根因（新 pod 未就绪就接流量、老 pod 被截断）已在 22:35 / 23:14 修完，
  但集群侧一直空白（仓库无 k8s 目录）：没有 preStop / `maxUnavailable: 0` / PDB / 探针接线。
- 做了：新增 `k8s/`（7 份清单 + README）：`00-namespace` / `10-configmap`（含
  `KEEP_ALIVE_TIMEOUT_MS`、`SHUTDOWN_TIMEOUT_MS`、`APP_VERSION`）/ `20-deployment`（`maxUnavailable: 0`
  + `minReadySeconds: 5` + `terminationGracePeriodSeconds: 60` + preStop `sleep 8` + 三类探针分工：
  `startupProbe`/`livenessProbe` → `/healthz`（不探依赖）、`readinessProbe` → `/readyz`）/
  `30-service` / `40-pdb`（`minAvailable: 2` + `unhealthyPodEvictionPolicy: AlwaysAllow`）/
  `50-ingress` + `51-ingress-sse`（SSE 单独一份关 `proxy-buffering`，靠最长前缀优先合并）。
- 关键判断：① `startupProbe` 用 `/healthz` 而非 `/readyz`（用就绪探针会让依赖故障时 pod 永远起不来）；
  ② 不在常规 Ingress 开启 `proxy-next-upstream: non_idempotent` —— 全站 POST，默认「非幂等不重试」才是安全值，
  排空做好后也不需要重试；③ Secret 只留文档不留模板文件（避免有人把 CHANGE_ME 直接 apply）。
- 验证：本机 docker-desktop 集群未启动，`kubectl --dry-run=client` 也要连 apiserver（实测不可用），
  故改用离线校验脚本（js-yaml 解析 + **39 项跨文件不变量断言**，验完即删）：grace(60) >
  SHUTDOWN(25)+preStop(8)、keepAlive(75) > 网关上游空闲(60)、headers > keepAlive、探针路径/超时分工、
  Service selector 与 targetPort 命名一致、ConfigMap 不含凭据、PDB minAvailable < replicas、
  SSE 关缓冲、镜像非 latest 且 `APP_VERSION` 与 tag 一致 —— 全绿。
- 附带发现（未修，已在 README 记为已知缺口）：运行镜像里**跑不了数据库迁移** —— `data-source.ts`
  在 `src/` 外不被编译、glob 指向 `src/database/migrations`、`db:migrate` 依赖 devDependency 的 tsx。
  故清单里没放迁移 Job，当前迁移只能从构建环境执行。
