**能力网关重定义 + 能力接入协议（设计稿）**：新增两份评审稿 —— [capability-protocol.md](../design/capability-protocol.md)（协议 v1：先定义「什么是服务 / 什么是网关」；服务名全局唯一且即 namespace、工具名只需服务内唯一、规范 key 与模型面名字**都由网关拼/拆**；模型面 `__` 映射、sync / 受理即完成 / task 三形态、回调五条铁律、任务归属、32 个工具新旧对照与别名迁移）与 [capability-gateway.md](../design/capability-gateway.md)（设计：网关 = 服务登记 + 能力治理 + 能力路由；服务不自注册，部署给地址、代码给能力；连接器退役并入外部接入；三段迁移路径；7 项待拍板）。

登记两条路径：内部服务代码声明（构建期收集）；外部团队（如 B 团队的订单服务）在自己服务里挂一个 `POST /invoke` 路由（约 30 行，不引 SDK、不做 MCP），再在后台填地址 / 鉴权 / 能力清单。外部服务的最小出站凭据因此进 v1。

核心取舍：砍掉自研注册中心 / 心跳 / `ai_tool_providers` 表（worker 个位数、Redis 心跳已够用；业界主流是网关配 target）；不自创工具描述格式，对齐 MCP 三件套；按安全边界拆服务（通用能力 / AI 数据域 / 外部接入），不按业务分类学划域。

查证结论：OpenAI function 名只允许 `[a-zA-Z0-9_-]`、≤64，Anthropic 同；MCP（SEP-986）允许 `/`。故规范 key 用 `namespace/tool`，模型面派生 `namespace__tool`。

评审拍板（同日）：网关 `tool-gateway` → **`capability-gateway`**，通用能力服务 `tool-worker` → **`common-capability`**；`tool_search` 与对外 MCP 端点先不做；任务完成自动唤醒会话、停止对话级联取消会话级任务；允许 http 联调（默认 https）；外部清单走 `GET /manifest` + 网关 30 秒探活，不做反向心跳；服务拆分为 exec / web / files / memory / skill 五个身份 + 网关内建 + 不登记的 plan / agent。

配置模型（待确认后落实现）：拆两层——新表 `ai_capability_services`（接入、鉴权、状态、默认 scope/limits、探活）+ 沿用 `ai_tools`（开关、限额、配置、密钥）；继承规则为「服务 disabled 短路 → 工具 enabled → scope 继承 → limits 取严」，探活失败只影响 `available`。

多实例（同日补）：**内部服务做负载均衡**——进程向网关登记实例（endpoint / maxConcurrency，心跳带 active），网关按 `active / maxConcurrency` 选最闲的实例、失败换一个，`task` 调用记一行 `taskId → 实例`；**外部服务只有一个 `baseUrl`**，不做 LB，多实例由对方 LB 吸收（协议 §4.6、设计稿 §6.5 / D14）。内部服务的存活靠心跳，不再单独探活。

登记接口（同日补）：两条路径共用一个 `POST /v1/services/register`——内部服务的**每个实例**启动时都调一次（幂等，body 里带自己的 `instance`：instanceId / endpoint / maxConcurrency），外部服务由 main 后台代提交（body 带 baseUrl，没有实例概念）；同一服务名可对应多个实例，`instanceId` 只需服务内唯一。网关是登记的唯一写方，后台只读目录；能力增删走 diff，不在清单里的转 `deprecated` 并保留配置行（协议 §4.7、设计稿 §6.6）。生命周期：启动 register → 每 10 秒 `POST /v1/instances/heartbeat`（只报 service + instanceId + active）→ 优雅停机 `POST /v1/instances/deregister` → 服务退役 `POST /v1/services/deregister`；`kill -9` 靠 30 秒心跳过期自动摘，任务靠 `taskId → 实例` 映射仍可查。**接口一律 POST + body，不用路径参数**（`taskId` 也走 `POST /tasks/get`），只有 `/healthz`、`/readyz` 探针是 GET。

**首轮会话命名：从「收尾时起名」改成「run 一启动就并行起名 + 整站 SSE 推送」**：命名不再等回答跑完 —— `chat` / `chatStream` / 排队执行三条路径在**解析完本轮模型**就把命名调用抛出去（`startFirstTurnTitle`），与主回答并行；输入从"本轮已落库的对话记录"改成**用户这条消息**（并行时助手回复还不存在），仍封顶 2000 字。起跑时先落兜底名（首条消息截 40 字 / 「新对话」），模型名回来再替换；替换前**重读一次标题**，已不是兜底那版就放弃（用户中途改名不被冲掉）。本轮 `abort.signal` 与 10s 超时合并（`AbortSignal.any`）交给命名调用，`stopRun` 一点，这次命名一起断。

**命名链路真正没通的两个原因（线上会话 `e7l7rsk8d35rwemgjgdh` 定位）**：用户发现新建会话的标题还是兜底名（`推荐一些可以让人成长的书单`）。查库：该会话只有一条 `model_gateway_usage`（主回答那次），命名调用**一次都没到网关**。两处叠加：

1. `title.service` 用 `decideModelForMastra(model).model` 当模型 —— 那只是 `{ id, apiKey: '' }` 描述；生产模型全走内部网关（真实 key 只在网关侧），Mastra 拿空 key 去官方端点，本地就抛错。改为 `toMastraModelInstance(model)` 造实例（与主回答同一入口，网关模式下带内部令牌 + 归因头），修完第一次真正打到网关。
2. 打到网关后又报 `ai.conversation.title_empty`：`maxOutputTokens: 32` 被推理型模型（`deepseek-flash`）的 reasoning 吃光，正文为空。改为 256 —— 实测一次命名 45 output token（40 是 reasoning）、耗时 1.2s，标题「个人成长书单」。

顺带发现 `memory-extractor.ts` 与 `summarizer.ts` 是同一个模型取法（`decideModelForMastra().model`），线上同样打不到网关 —— **已一并修**（都改成 `toMastraModelInstance`）。真实网关实测：压缩调用 output 417（354 是 reasoning）、记忆抽取 output 67（44 是 reasoning），两者原有 800 / 400 的预算够用，不用调。新增 `test/ai-title-model.test.ts` 钉住"必须走 `toMastraModelInstance`"。
