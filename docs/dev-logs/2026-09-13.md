## 00:33 修复 `pnpm dev:server` 启动失败：tsx 的 CJS/ESM 双实例

- 现象：`pnpm dev:server` 启动即抛
  `UnknownDependenciesException: Nest can't resolve dependencies of the LoggerModule (pino-params, ?)`
  （`ApplicationConfig at index [1]`），发生在 InstanceLoader 装配 LoggerModule 时。
- 定位（先复现再判因）：
  ① 最小复现：在 kits 里单跑 `LoggerModule.forRoot()`（nestjs-pino 的模块，不经我们的封装）同样失败
     → 与我们 `LoggerModule` 的 imports/exports 写法无关；
  ② 读 nestjs-pino@5.1.0 dist：其 `LoggerModule` 构造器是
     `(@Inject(PARAMS_PROVIDER_TOKEN) params, applicationConfig: ApplicationConfig)`，第二个参数靠
     `design:paramtypes` 注入 `@nestjs/core` 的 `ApplicationConfig`；
  ③ 读 @nestjs/core@12 源码：`ApplicationConfig` 已不是全局 provider，而是
     `Module.addCoreProviders() → addApplicationConfig()` **逐模块注册**，token 就是该类本身；
  ④ 关键一步：用 `createRequire` 对比发现 `require('@nestjs/core')`（nestjs-pino 的 CJS 路径）与
     `import '@nestjs/core'`（我们的 ESM 路径）拿到**两个不同的 `ApplicationConfig` 类**，
     于是元数据里的 token 与 Nest 注册的 token 对不上；

     原生 node ✓ —— 结论：问题出在 tsx 同时注册的 CJS 钩子，只挂 ESM 加载器时 `require(esm)`
     复用同一份 ESM 缓存，行为与 `node dist/main.js` 一致。

## 00:50 调研「能不能改用 `nest` 命令」：TS 7 阻塞，维持 tsx/esm

- 动因：`dev:server` 现在要写 `node --watch --import tsx/esm`，不如 `nest start --watch` 常规；
  且 rihel-base 用的就是标准 nest CLI（`dev: nest start --watch`、`build: nest build` + `nest-cli.json`）。
- 调研（不动本仓库依赖，把 CLI 装到 /tmp 单跑）：
  ① `@nestjs/cli` 最新 12.0.0（对应 Nest 12），依赖面 14 个直接依赖（@angular-devkit/*、chokidar、
     commander、ora、tsconfig-paths、自带 typescript…）；
  ② 用 /tmp 的 CLI 对 `apps/server` 跑 `nest start --watch`，**直接失败**：
     `The installed TypeScript version (7.0.2) does not expose the programmatic compiler API that the
     Nest CLI requires. TypeScript 7.0 ships the "tsc" executable only; the compiler API is expected to
     return in 7.1. Please install TypeScript 6 (e.g. "npm i -D typescript@^6") until then.`
  ③ 读 CLI 源码定位：守卫在 `lib/compiler/typescript-loader.js` 的 `assertProgrammaticApiIsSupported`
     （检查 `ts.getParsedCommandLineOfConfigFile`），而该 loader 被 `actions/build.action.js`
     **无条件加载** → tsc / swc / webpack / rspack **任何 builder 都过不去**（webpack 另有独立限制：
     对 ESM 工程直接抛错）；
  ④ 本仓库 TS 版本核对：root / packages/* / apps/* 共 9 处全部 `^7.0.2`，实际 `tsc --version` = 7.0.2。
- 结论：**在 TypeScript 7.0.2 下 `nest build` / `nest start` 不可用**（不是 tsx 的问题，换成 nest 也不能
  顺带绕开前一轮的双实例坑，只是换了个原因）。可选路线：
  A. 维持现状（推荐）：`node --watch --import tsx/esm` + `tsc` 构建，零新依赖、保住 TS 7 原生速度；
  B. 降 TypeScript 到 6 换 nest CLI：失去 TS 7 编译速度，多一整套 @nestjs/cli 依赖 + `nest-cli.json`；
  C. 等 TS 7.1 的 compiler API 回归后再切 `nest start --watch`（届时本工程 ESM 配置基本可直接用，
     已单独验证 `node dist/main`（无扩展名入口）在 Node 24 下能正常启动，不额外需要 entryFile 变通）。
- 落地：本轮只把结论写进 `apps/server/README.md`「开发须知 → 为什么不用 nest CLI（TypeScript 7 阻塞）」，
  代码与依赖零改动。
- **决定（用户选定）**：走 A —— 维持 `node --watch --import tsx/esm` + `tsc` 构建，不为 nest CLI 把
  TypeScript 降到 6；待 TS 7.1 编程式 API 回归后再评估切 `nest start --watch`。

- 坑点：rihel 的时间轮写的是 `maybePromise(task.exec(...)).catch(...)`，**exec 同步抛错时 maybePromise
