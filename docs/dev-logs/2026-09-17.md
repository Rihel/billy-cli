## 21:30 修复：SSE 三个真问题 + 异常过滤器在 headersSent 时二次崩溃

- 做了：① 控制器身份改读 ALS，订阅解析提前到 `writeHead` 之前；② `writeHead` 后补 `response.flushHeaders()`
  —— Node 要等第一次 write 才 flush，而长连接下一次写可能是 15s 后的心跳，客户端 fetch 不 resolve、
  状态一直卡 `connecting`，前置网关还可能先掐断；③ `AppExceptionFilter` 增加 `response.headersSent`
  分支：记日志 + `end()`，不再调 `response.json()`。
- 坑点：排障时日志只显示 `error: {}` —— 日志工厂没挂 Error 序列化器，`JSON.stringify(Error)` 就是 `{}`，
  首因被埋了；真凶靠读 `currentUserId()` 的实现才定位到。
- 解决：用真实 HTTP 探针（SDK 走完整链路）验证 6/6：管理员建连即 open → `monitor.test` → 收到
  `alert.fired` 且负载过 schema → `close()` 终态 → 前台用户 `auth: 'both'` 建连 → 前台用户收不到管理员
  广播（显式请求 `admin:all` 也被忽略）。已记进 `docs/design/frontend-foundation.md` §8。

## 23:05 修复：SSE 长连接的请求日志 requestId 丢失（8.5 记的那个缺口）

- 做了：`RequestLoggerMiddleware` 改为**注册时捕获 requestContext 的 store 引用**，不再在
  `finish` / `close` 时现取 `requestContext.get(...)`；补两条回归用例（作用域外触发 finish、
  守卫写入身份后触发 close）。
- 坑点：现有单测的注释写着「真实场景里 finish 由 Express 在 ALS 上下文内触发」—— 普通请求确实如此
  （`res.end()` 同步发生在处理链路内），**长连接不是**：SSE 的响应结束来自 `await connection.closed`，
  是 socket 的 close 回调 resolve 的，那时 `run()` 的作用域早就退出（它在 `next()` 返回时就结束）。
  所以这个 bug 骗过了单测，也骗过了普通请求的日志。
- 解决：store 是可变共享对象，持有引用即可（守卫后写入的 userId / adminId 照样读得到）。
  **反向验证**：换回旧写法跑单测，两条新用例必挂（2 failed）；改回后全绿。真实 server 实测
  SSE 响应头 `X-Request-Id: zszjtpzqjkshjn2v` 与日志 `requestId` 同值，`adminId` 也在。
