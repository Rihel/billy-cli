# AI 文件能力复盘：从“附件”到“文件系统”

## 一句话

文件这块真正难的不是上传、下载或预览，而是**同一份文件同时活在两个世界**：一个是 AI 执行用的 workspace，一个是用户交付用的对象存储。所有设计、坑和返工，基本都围绕这两者的边界展开。

## 一、最初把它想简单了

一开始很容易把需求理解成“给会话加一个文件列表，再做个预览”。

实际做下来，文件至少有三层：

1. **执行层**：AI 要读、写、搜、替换，文件必须落在它当前 Pod 能访问的 workspace；
2. **交付层**：用户要长期看到、预览、下载，文件必须进对象存储，不能依赖某个 Pod 的本地盘；
3. **展示层**：同一份文件在会话页、后台文件页、文件预览弹窗里都要有一致的身份、权限和生命周期。

所以它不是“附件功能”，而是一个小型的文件系统：有路径、有来源（user / ai）、有归属会话、有软删除、有版本覆盖、有临时物化、有权限边界。

## 二、五个关键判断

### 1. 执行面与交付面分离

- workspace 是**临时执行面**：Pod 本地、可读写、随运行环境变化；
- OSS 是**持久交付面**：用户可见、可下载、可审计；
- `file-submit` 负责 workspace → OSS，`file-download` 负责 OSS → workspace；
- 两边不假装是同一份文件，桥接动作显式发生。

这个判断后来救了很多次：AI 在 workspace 里怎么折腾都不会污染用户文件；要交付时必须显式 submit，责任清晰。

### 2. 文件树是“会话内的逻辑路径”，不是磁盘路径

`(conversation_id, path)` 唯一，source 区分 user / ai，软删除保留审计。OSS key 是另一套物理地址，由后端拼，不暴露给模型。

这样模型只需要理解“会话内的路径”，不需要知道 bucket、owner、runId 这些基础设施细节。

### 3. 预览走“前端直连对象存储”，后端只做控制面

最初的 Office 预览是后端下载文件再转发给前端。用户明确要求：

> 前端直接请求 OSS 的链接拿到文件流，不要走后端下载转发，后端只提供链接。

于是改成：

- 后端只负责签发 `getDownloadUrl`，或者把 workspace 文件物化到 OSS 的 `_preview/`；
- 浏览器自己 `fetch` 文件流；
- Word / Excel / PPT 分别用 `docx-preview` / SheetJS / `pptx-preview` 在浏览器渲染；
- 后端不再承担文件字节的转发带宽。

代价是部署必须保证 bucket CORS（GET/HEAD）和可读性；S3/COS 启动时会尝试配置 CORS，失败只告警，不阻塞启动。

### 4. 预览是一个独立产品面，不是弹窗里的一个 iframe

后来逐步补成：

- 默认全屏；
- 左侧文件列表，支持上一个 / 下一个；
- 键盘 `↑/↓` 切文件，PPT `←/→` 切页；
- 图片 / 视频 / PDF / HTML 铺满容器，DOCX / XLSX 铺满宽度，PPTX 单页自适应；
- Markdown 使用聊天同款 Streamdown，`xflow` / `json` 围栏正常渲染；
- HTML 用沙箱 iframe，并拦截会跳转到后台页面的链接。

这些不是“样式细节”，而是预览从“能看”变成“能用的工具”的必要条件。

### 5. 手机端要换交互模型，不是只加 CSS

真实问题是：会话列表在手机上直接隐藏，用户没有入口；右栏还按桌面分栏挤压正文；页头所有元素都显示。

最后做的不是简单 `hidden`：

- 断点从 768 提到 1024，平板竖屏也走手机布局；
- 会话列表改为页头入口 + 全屏 Sheet；
- 右栏改为手机全屏 Sheet，覆盖默认 `w-3/4` 限制；
- 页头隐藏 agent / run / 复制等次要项；
- 去掉挡住输入框的会话 FAB。

移动端的关键不是“把桌面缩小”，而是**在窄屏下重新安排入口和层级**。

## 三、踩过的坑，按真实顺序

1. **会话列表不能滚动**：先以为是 CSS，实际是只取了第一页 20 条；用户有 55 条。改成 `useInfiniteQuery` + 触底加载才对。
2. **HTML 预览多一层工具条**：全屏弹窗里又套了沙箱自己的“HTML / 全屏 / 重跑”，加了 `frameless` 才干净。
3. **HTML 里的链接跳后台**：相对链接按父页面解析，点一下 iframe 就导航到后台；最后在沙箱文档里注入 link guard，只放行 `#` 锚点。
4. **PPTX 两个、黑边、控件压住页面**：`pptx-preview` 的 list / slide 模式、固定 viewPort 与内部二次渲染都踩了一遍；最后改成 `load()` + 手动 `renderSingleSlide`，控制条放滚动区外。
5. **Office 走后端代理**：能用，但违背“直连 OSS”的要求；删掉 binary 接口，改 workspace-link 物化，才把数据面收干净。
6. **手机 922px 还是桌面布局**：断点 768 不够，页头元素全显示，子助手卡文字竖排；提到 1024 并重排页头才解决。
7. **局域网访问失败**：先怀疑 Next / CORS / localhost URL，最后 `8080` 测试服务也不通，Mac ping 手机 100% 丢包、ARP incomplete，确认是路由器客户端隔离，不是应用层。

这些坑的共同点是：**先验证真实故障点，再改代码**。尤其是“滚动不了”和“手机访问不了”，表面上都像 UI/接口问题，实际分别在分页和二层网络。

## 四、子助手与文件

文件工具最初对子助手是 `child: 'deny'`，理由听起来合理：workspace 共享，父 agent 统一读写。

但实际任务里，子助手需要读现有材料、写自己的交付文件，父 agent 不可能替它做所有文件操作。所以后来放开了文件工具：

- 子助手可以 `file-list` / `read-file` / `file-search` / `workspace-files` / `write-file` / `replace-file` / `append-file` / `file-download` / `file-submit`；
- 共享 workspace 没有跨 run 文件锁，父 agent 必须给不同子助手分配不同路径；
- 子助手崩溃后不做 durable 恢复：父 run 重放 `run-sub-agent` 时，同一个 `(parent_run_id, tool_call_id)` 复用被标 `interrupted` 的子 run 原地重启；**不是断点续跑，任务从头执行**，旧时间线保留审计，工具必须幂等。

这块的边界要诚实：能重新激活，不等于能无损续跑；恢复会重跑、会花钱。

## 五、现在的边界

还没做完或刻意没做的：

- `_preview/` 临时对象需要 bucket lifecycle 清理；
- 子助手并发写同一文件没有锁，靠父 agent 分配路径；
- 老 `.doc` / `.ppt` 只支持下载，不做浏览器渲染；
- workspace 的图片 / PDF / 视频预览仍走 `/agent/file/workspace-content`，没有完全统一到“前端直连”；
- bucket 目前偏 public-read + CORS，key 泄露仍意味着可下载；
- 手机端其他后台列表页、表格还没有逐页做真实设备验收；
- 局域网访问在路由器客户端隔离下无解，需要改路由器或走 Tailscale / 隧道。

## 六、如果继续做

1. **统一数据面**：workspace 的所有可预览类型都走“物化 + 直连”，把 `workspace-content` 收敛成仅下载；
2. **补生命周期**：`_preview` TTL、失败清理、配额与用量告警；
3. **补并发边界**：子助手文件写入的路径约定或租约，避免共享 workspace 互相覆盖；
4. **把预览当产品验收**：真实手机、真实 Office 文件、真实 bucket CORS，而不是只看构建通过；
5. **权限再收紧**：bucket 私有化 + 短时签名，减少“key 泄露即可下载”的风险。

## 结尾

文件能力最后做出来的不是“一个上传按钮”，而是一条完整的链路：

**模型能读写 → 文件能交付 → 用户能预览 → 后台能管理 → 手机能用 → 崩溃能恢复。**

真正决定质量的，不是某个渲染库，而是这些边界有没有被说清楚、守住，并且在出问题时能不能快速定位到是哪一层。
