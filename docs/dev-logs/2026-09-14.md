## 00:45 修复 HttpStreamClient：页面恢复可见后静默断流

- 现象（用户报「stream Client 有 bug」）：浏览器切走标签页再切回，SSE 流永久失效，
  状态停在 `closed` 且不再重连——而 `openWhenHidden` 的文档契约正是「隐藏时断开、恢复后自动重连」。
- 根因：`AbortController` 只在 `connect()` 里创建一次，整轮重连循环复用同一个 signal。
  AbortSignal 一旦 abort 就**永久**处于 aborted，于是隐藏触发的 abort 之后，恢复可见时的
  重连请求带着已 aborted 的 signal 发出 → transport 把它当「正常结束」resolve → 状态机
  `setState(Closed); break`，静默进终态。同一根因还让 `delay()` 立即返回（signal 已 aborted）。
- 修复：把 AbortController 移到 `run()` 的**每次连接尝试**里新建（`close()` 仍中断当前这次）；
  顺带在 `onOpen` 重置 `retryCount`——原来只增不减，跨多次重连后偶发断线也要等满 30s 退避。
- 坑点：① 新写的回归测试**第一版带修复也失败**，因为测试桩的 fetch 没模拟「真实 fetch 在
  abort 时会终止 body 流」，`reader.read()` 永远挂起、`closed` 永不 settle，循环走不到第二次；
  补上 signal→controller.error() 后才复现。② 现有 90 个单测全绿却漏掉这个 bug——因为
  `document` 相关分支在 node 环境根本没被测过（这次用最小 document 替身补上）。
- 验证：把 src 临时 revert 后跑新测试 → `AssertionError: expected 'closed' to be 'open'`（证明用
  例真的能抓）；恢复修复 → http-client 92 / kits 111 / server 24 单测全绿，build:pkgs 4/4。

## 02:00 修 TimeWheel：stop() 后仍会执行已派发的任务

- 现象：加日志改造后跑 kits 单测，`time-wheel` 的「stop 后 tick 循环停止」偶发失败
  （`expected 3 to be 2`）。
- 根因：`tick()` 把命中任务 `nextTick()`（setImmediate）派发到下一个事件循环，回调里不检查
  是否已 `stop()`，所以停表后仍会蹦出一次执行。原来那个断言是等概率踩中的 flaky。
- 解决：派发回调开头加 `if (!this.isRunning) return`（`isRunning` = 定时器存在），
  让 `stop()` 成为真正的停止；测试断言保持不变（不靠放宽断言掩盖问题）。
  连跑 3 次 121 用例全绿。

## 02:30 设置 HTTP 长连接超时（对齐 Kong 前置）

- 背景：用户问 keepAliveTimeout 现在多少、前面挂 Kong 会怎样。查证：全仓**零设置**，
  走 Node 默认（实测本机 Node 24.14.1 → keepAliveTimeout=5000 / headersTimeout=60000 /
  requestTimeout=300000），线上响应头确实是 `Keep-Alive: timeout=5`。
- 问题：Kong 上游连接池默认 `upstream_keepalive_idle_timeout=60s`（官方 kong.conf.default 核对：
  pool_size 512 / max_requests 10000 / idle 60），且 **OpenResty/Nginx 不认后端响应头的
  `Keep-Alive: timeout=N` 提示** → 后端 5s 关、网关 60s 内仍认为可复用 → **[5s,60s] 窗口内
  往正在关闭的 socket 发请求 → 间歇 502**，且后端日志无痕（请求没到应用），极难定位。
- 做了：按用户确认取值落地 —— Kong 侧保持默认 60s，后端 `keepAliveTimeout=75s`、
  `headersTimeout=80s`。`server` 配置分片新增两字段（env `KEEP_ALIVE_TIMEOUT_MS` /
  `HEADERS_TIMEOUT_MS`），`main.ts` 在 `listen` 前写入 `app.getHttpServer()`；
  并用 `superRefine` 校验 `headersTimeout > keepAliveTimeout`。
- 坑点：① Node 对 `headersTimeout ≤ keepAliveTimeout` **不报错、静默接受**（实测赋值成功、
  无异常），所以必须在配置层自己拦；② 给 schema 加 `superRefine` 前先验证会不会破坏 kits 的
  「默认值物化」——实测 Zod 4 下 `def.type` 仍是 `object`、`shape` 可读，物化不受影响。
- 验证：响应头由 `Keep-Alive: timeout=5` 变为 **`timeout=75`**；**空闲复用对照实验**——
  同一 TCP 连接空闲 10s/30s 后再请求，75s 实例 ✅ 两次都 200，而 `KEEP_ALIVE_TIMEOUT_MS=3000`
  的对照实例 ❌ 只收到 1 个响应（探针有牙齿，不是假绿）。server 单测 33（新增 3）。
- 附带：README 新增「前置反向代理（Kong / Nginx / LB）」一节（keep-alive 竞态 /
  SSE 必须 `response_buffering=false` / `RATE_LIMIT_TRUST_PROXY`），stream skill 同步 SSE 网关注意事项。
