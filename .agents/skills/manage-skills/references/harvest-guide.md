# 从开发经验回收沉淀 skill（manage-skills 引用文件）

> 本文件是 `manage-skills` skill 的组成部分。
> 开发中解决了一个有价值的问题，把**解决思路回收、抽象、精简成可复用的 skill** 时必读。

## 1. 触发时机

开发中（尤其踩坑、复杂方案、通用模式）解决之后，判断是否值得沉淀成 skill：

- **可复用**：会反复出现，或其他模块也会遇到（不是一次性）。
- **有明确规范 / 产出**：不是一句经验，而是有步骤、有产出、可遵循。
- **对齐工程**：能落到 billy 的某个分层 / 包 / 目录（`placement.md`）。

满足以上才沉淀；只满足「这次解决了」不满足「可复用」的，留在 `dev-log` 即可。

## 2. 回收流程（从经验 → skill）

1. **记录**：先按 `dev-log.md` 记下「做了什么 / 坑点 / 怎么解决」。
2. **提炼**：去掉一次性细节，抽象出**可复用的思路 + 步骤 + 关键代码片段**。
3. **对齐**：映射到工程分层（按 `placement.md` 定放置位置），确认该能力的位置。
4. **成 skill**：按 `create-guide` 写 `SKILL.md`（frontmatter + 核心要点 + 参考文件 + 检查清单）。
5. **登记**：在 `catalog.md` 与 `README.md` 登记。

## 3. 抽象精简的原则

- **去特化**：把「这次这个问题的解法」，泛化成「遇到这类问题怎么做」。
- **保关键**：保留坑点、边界条件、可复现的失败路径——这正是复用价值所在。
- **够用就好**：只沉淀真正可复用的部分，不为凑数建 skill（不重复造轮子，先确认现有
  skill 未覆盖）。
- **留证据**：skill 里附一个真实参考实现 / 示例，供 agent 对照，而非纯讲理论。

## 4. 和 dev-log 的关系

```
开发中解决一个问题
   → 记入 dev-log（做了什么 / 坑点 / 解决）
   → 判断是否「可复用 + 有规范 + 对齐工程」
        ├─ 是 → 回收沉淀成 skill（本文件流程）
        └─ 否 → 留在 dev-log 即可，不成 skill
```

- **dev-log 是回收的素材库**：坑点与解法先沉淀在日志。
- **重要的、可复用的 → 升级成 skill**；一次性的 → 留在日志。
- 这样 dev-log 是「过程记录」，skill 是「提炼后的可复用规范」，两者互补。

## 5. 完成检查清单

- [ ] 该经验确实可复用（会反复出现 / 其他模块也会遇到），非一次性
- [ ] 已去特化、保留关键坑点与边界，附真实参考实现
- [ ] 按 create-guide 写成规范 skill 并在 catalog / README 登记
- [ ] 未与现有 skill 重复（不重复造轮子）
