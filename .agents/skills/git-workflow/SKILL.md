# Git 提交与工作流

前置：先加载必读 skill `billy-dev-foundation`（工程约定）。

## 1. commit message 规范（中文）

格式：**`<类型>：<一句话摘要>`**（类型后中文冒号，摘要概括改动意图，≤50 字）。
同一提交多要点时，可在摘要后空行加分点（`- ` 列表）。

| 类型 | 场景 | 示例 |
| --- | --- | --- |
| 新增 | 新功能 / 新模块 / 新页面 | `新增：商品模块的 CRUD 接口与页面` |
| 重构 | 不改行为的结构调整 | `重构：拆出 @repo/http-client 通用客户端` |
| 修复 | bug 修复 | `修复：重置密码 token 过期未校验` |
| 变更 | 行为/接口变更（非新增非修复） | `变更：列表接口排序默认值改为 updatedAt` |
| 文档 | README / docs / skill 等 | `文档：补充前端页面开发规范` |
| 测试 | 测试新增或修改 | `测试：补充 HttpClient 刷新重试用例` |
| 配置 | 依赖、构建、环境配置 | `配置：vitest 接入 http-client 包` |
| 样式 | 纯样式 / UI 微调 | `样式：登录页移动端品牌区布局` |
| 杂项 | 其他（格式、小修） | `杂项：清理无用 import` |

不要用无信息量的提交（如 `update` / `fix` / `wip`）；摘要要能独立看懂改了什么、为什么。

## 2. 提交粒度

- **一个逻辑变更一个提交**：新功能、重构、修复、文档各归各的，不要混在一个提交里。
- 多文件改动先拆分：`git add <路径>` 分批暂存，再分别提交（用 `git status` 核对）。
- 不提交：调试残留（console.log / 临时文件 / 本地 .env）、未完成的半成品、
  与本次无关的格式化噪音。
- 提交前自问：这个提交能独立回滚且不破坏其他功能吗？

## 3. 辅助提交流程（agent 执行时）

1. `git status` 查看改动，`git diff`（未暂存）与 `git diff --cached`（已暂存）审查内容。
2. 判断是否满足第 2 节粒度；不满足则按文件/逻辑分组 `git add`。
3. 依据第 1 节生成 commit message（类型 + 摘要 + 必要分点）。
4. `git commit -m "..."`（多行用 `-m` 多次或 heredoc）。
5. 提交后 `git log --oneline -3` 确认。

**不擅自执行**：`push` / `pull --rebase` / `force` 等影响远端或他人工作的操作，
除非用户明确要求；需要时先说明再执行。

## 4. 工作流习惯

- 开始新任务前先 `git status` 确认工作区干净（有未提交改动先询问是否提交）。
- 中途不要随意 amend 已推送的提交；本地未推送的提交 amend 需说明理由。
- 提交信息风格与历史保持一致（中文、类型前缀），存量历史（如纯英文 `update`）
  不强制回改，新提交从规范开始。

## 5. 完成检查清单

- [ ] message 符合 `<类型>：<摘要>` 中文格式，类型用第 1 节词表
- [ ] 一个提交只含一个逻辑变更，无调试残留 / 无关文件
- [ ] 已用 `git diff` 审查暂存内容后再提交
- [ ] 未擅自 push / 变基 / 强推；远端操作用户确认后执行
