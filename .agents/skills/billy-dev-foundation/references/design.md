# 设计决策与方案（billy-dev-foundation 引用文件）

> 本文件是 `billy-dev-foundation` skill 的组成部分。
> 拿到非平凡需求时，先评估难度决定要不要出设计方案，再决定直接做还是先设计。

> **首要准则先行**：工程最高准则（实事求是、抓主要矛盾等 8 条）见
> `billy-dev-foundation/references/principles.md`（权威版见仓库根 `AGENTS.md`）；
> 本文件是它在「设计」环节的展开。

## 1. 先评估难度，决定要不要出设计方案

按需求复杂度分级：

| 难度 | 特征 | 处理 |
| --- | --- | --- |
| 简单 | 单表 CRUD、改字段、修 bug、加一个页面 | 直接按现有 skill 位置做，**不必写设计文档** |
| 中等 | 跨模块、多实体关联、有状态流转、引入新基础设施能力（队列 / 缓存 / 锁） | 先出**简短落地方案**（位置 + 关键数据结构 + 关键流程，写入 `docs/design/`），再动手 |
| 复杂 | 架构级改造、性能 / 并发 / 分布式、多服务协作、影响面大 | 必须**先出完整设计方案**（写入 `docs/design/`），评审通过后再实现 |

判断依据：影响面（改多少层 / 包）、是否引入新依赖、是否涉及状态 / 并发 / 一致性、
能否简单回滚。

## 2. 设计方案的原则

- **系统化思维（最高优先）**：把需求放进**整个系统**里看，而非孤立看单点功能——
  - 全景视角：它和既有模块（auth / todo / storage…）、既有基础设施（DB / Redis /
    ObjectStorage）的关联与边界是什么，处于系统数据流的哪个位置。
  - 影响面：改这里会波及哪里——数据流上下游、共享数据结构、依赖方向，先评估再动手。
  - 从整体到局部：先画出「它属于系统的哪个位置、和谁交互」，再落到具体位置
    （`placement.md`），而不是一上来就写局部代码。
  - 生命周期与演进：不只满足当下，考虑它如何随系统一起演化、能否独立替换 / 下线。
  - 边界条件：失败、异常、并发、空态、扩展时的行为是否想清楚。
- **顶层角度**：从「工程分层与依赖方向」出发（`apps/server → kits → shared`），
  不只在局部打补丁；新能力先想清楚它属于哪一层（见 `placement.md`）。
- **长远目标**：考虑扩展性——新需求来了好不好加、要不要预留演进空间；避免为眼前
  需求把结构写死。
- **可维护**：职责单一、命名清晰、遵循工程既有模式（见 `placement.md` / `code-conventions.md`）。
- **可测试**：依赖可注入（构造器注入）、纯逻辑与 IO 分离、关键路径可单测
  （见 `write-tests` skill）。
- **文档位置**：设计落地方案写成 Markdown 文档，统一放 **`docs/design/`** 目录，命名
  kebab-case 主题名，如 `docs/design/<feature>.md`；不在代码目录里散落设计文档。

## 3. 想不到方案时：借鉴 → 借鉴不到则回归第一性原理

1. **抽象本质**：先想清楚「要解决的本质问题」是什么——把它抽象成通用问题
   （状态管理、任务队列、一致性、限流、幂等、重试…），而不是陷在具体功能里。
2. **找成熟方案 / 现成 skill 借鉴**：
   - **成熟方案**：成熟开源项目的设计、成熟库的架构、行业通行做法，借鉴思想而非照抄。
   - **现成 skill**：联网搜索并加载该领域**现成的 agent skill**，直接获得一份可复用的
     任务规范（怎么找 / 评估 / 接入见 `manage-skills` 的 `find-external-skill.md`）。
   无论哪种，都把**适用的思路**映射回本工程的既有分层与模式（结合 `placement.md` 定放置位置），
   而不是整体搬代码。
3. **借鉴不到（或找不到现成方案）→ 回到第一性原理**：
   - **回归设计本质**：从问题本身出发，推导「这个能力最朴素的形态应该是什么」，
     不被具体技术栈或他人实现框住。
   - 用**设计模式**建模：策略 / 观察者 / 状态 / 模板方法 / 装饰 / 工厂 / 仓储 /
     统一入口 / 适配器等经典模式，以及架构模式（分层、端口-适配器、事件驱动、CQRS…）。
   - 用**心智模型**校验：领域建模、职责单一（SRP）、依赖倒置（DIP）、开闭原则、
     组合优于继承、纯逻辑与 IO 分离、可观测性等第一性原则。
   - 推导出的方案**仍要落回本工程分层与既有模式**（`placement.md` + `code-conventions.md`），
     不是凭空造一套新架构。
4. **够用就好**：只借鉴 / 采用需要的部分，不引入远超需求的复杂度（见
   `code-conventions.md` 第 10 条与 `docs/sdk-refactor.md` 的教训）。

## 4. 落地顺序

1. 评估难度 → 决定要不要出设计方案。
2. 需要设计 → 写方案：**位置（placement）+ 关键数据结构 + 关键流程 + 测试点**。
3. 想不到 → 借鉴成熟方案 / 联网找现成 skill；都没有 → 第一性原理 + 设计模式 / 心智模型 → 映射回本工程位置。
4. 评审 / 自查 → 按 `workflow.md` 实现 → 对照完成检查清单。

> 核心原则：**小步快走，大改先设计**。简单需求不套重流程；复杂需求不在没想清楚
> 位置与结构还没定就动手写代码。
