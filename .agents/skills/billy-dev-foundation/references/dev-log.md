# 开发日志规范（billy-dev-foundation 引用文件）

> 本文件是 `billy-dev-foundation` skill 的组成部分。
> 每次开发结束都要记录日志，按本文件的三段式写法，落到 `docs/dev-logs/yyyy-MM-dd.md`。

## 位置与约束

- 文件：`docs/dev-logs/yyyy-MM-dd.md`（按当天日期命名，跨天分开）。
- 同一天多次开发：**追加**到同一文件，不要新建覆盖。
- 单次记录 ≤ **500 字符**，精炼，只记关键信息。

## 三段式内容（每次记录都覆盖）

1. **做了什么事**：本次改动的目标与范围——改了什么模块 / 文件，新增或修了什么（一句概括 + 关键落点）。
2. **遇到了什么坑点**：过程中踩到的坑——报错、设计冲突、第三方库行为、并发 / 数据一致性问题、性能陷阱等。
3. **怎么解决的**：如何定位与解决——关键决策与结论，供日后回溯复用。

## 格式建议

```markdown
## <HH:mm> <主题 / 模块>

- 做了：<一句话说明改动目标与范围>
- 坑点：<踩到的坑，具体、可复现>
- 解决：<定位方式 + 解决方案 + 关键决策>

---   ← 每条记录之间用分割线隔开，同一天追加时清晰分层
```

## 示例

```markdown
## 14:20 商品模块列表接口

- 做了：加了商品 CRUD 的 page-query 接口和 SDK 方法，顺带实体 + 迁移。
- 坑点：卧槽，游标分页在 PG 下 updatedAt 一样直接重复数据，我 tm 调了半天才搞明白。
- 解决：淦，加个 (updatedAt, id) 复合索引 + id 兜底排序就完事了，复用 @repo/db 的 cursorPageWith。

---

## 16:05 修复订单状态机并发覆盖

- 做了：给订单状态转移加了乐观锁，防止多实例并发把状态改串。
- 坑点：md，没加锁之前两个请求同时改 status，后写的把先写的覆盖了，单测都复现不出来。
- 解决：实体加 version 列，update 带版本号 CAS，冲突就重试，总算稳了。
```

## 原则

- **记录坑点优先**：成功路径人人会写，坑点与解法才是日后的价值。
- **可回溯**：写到能让自己（或别人）三个月后一眼看懂「当时为何这么做」。
- **宁短勿空**：500 字符上限内写清楚三件事即可，不凑字数、不写流水账。
- **贴吧暴躁老哥语气**：内部开发日志就按暴躁老哥那味儿写，脏话随便来（我草 / 卧槽 /
  tmd / 淦…），不用装文明、不用修饰措辞——真实、解压、有记忆点，越糙越能记住当时
  为啥被卡住。
  **边界**：仅限 dev-log / 内部开发记录；对外文档、用户可见文案、commit message、
  正式设计文档（`docs/design/`）仍保持规范严谨，不适用本条。

## 日志的用途（写它是为了被用）

日志不是写完就归档，它服务于后续开发：

1. **开工前查**：新任务先 `grep docs/dev-logs/` 相关模块，了解历史坑点与解法，
   避免重复踩坑（即「不重复造轮子」在知识层的体现）。
2. **排障检索**：遇到问题时先翻日志找同类问题的解决方式，复用而非重推。
3. **知识沉淀**：坑点与解法是工程的隐性知识；重要且通用的坑，同步存入长期记忆，
   跨会话生效。

正因如此，记录时务必「坑点写得可复现、解决写得可复用」——你是在给未来的自己和
同事铺路，而不是完成一个归档动作。
